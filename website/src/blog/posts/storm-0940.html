I work at an MSSP. Our clients trust us with access to their environments, and so do the vendor tools we connect to their tenants. This post is about what happens when one of those trusted tools is turned against every customer at once, and the attacker driving it is a team of AI agents that does not sleep.

In October 2026, Microsoft attributed a supply chain compromise of ConnectWise Cloud Backup (formerly SkyKick Backup) to Storm-0940, a China-aligned actor active since 2021. Using a stolen credential of the backup application and ARTEX, an open-source multi-agent AI pentest framework, the actor attempted sign-ins to more than 2,250 Microsoft 365 tenants. In some of them it went from first touch to privileged cloud access in under three hours. In one, an application gave itself Global Administrator and planted new secrets in other applications, including a security vendor's own app, in about five minutes.

No user typed a password. No phishing email. No endpoint was touched, so no EDR saw anything. Every step was an API call to Microsoft's cloud, and every step left a trace in logs that most SOCs either do not collect or never look at. This post goes deep on how the app-only path works, where it shows up, and how to detect it in Cortex XDR and Splunk. The four new rules are in my detection library as DL-0076 to DL-0079, and you can paste raw Entra ID audit or sign-in JSON into the playground to see them fire.

Why the usual defenses never fired

To understand the detections you have to understand the path, because it is not a user path at all.

One secret, every tenant

A SaaS backup service is registered in Microsoft Entra ID as a multi-tenant application. The application object lives in the vendor's tenant. When a customer connects the service, an administrator grants admin consent, and Entra creates a service principal for that app inside the customer's tenant, with the application permissions the vendor asked for (to read every mailbox, every OneDrive and SharePoint site, Teams, the directory). From then on the vendor's backend does not need anyone to sign in. It uses the OAuth 2.0 client credentials flow with the app's secret or certificate, once per customer tenant:

POST https://login.microsoftonline.com/<customer-tenant-id>/oauth2/v2.0/token
Content-Type: application/x-www-form-urlencoded

client_id=506e08f9-6e9a-4da4-942b-a099a03644ae      # ConnectWise Cloud Backup
&client_secret=<the vendor's credential>
&scope=https://graph.microsoft.com/.default
&grant_type=client_credentials

The token that comes back is an app-only token. Decoded, the parts that matter look like this (illustrative values):

{
  "aud":   "https://graph.microsoft.com",
  "tid":   "<customer-tenant-id>",
  "appid": "506e08f9-6e9a-4da4-942b-a099a03644ae",
  "idtyp": "app",
  "roles": [ "...the application permissions the customer consented to..." ]
}

Read that again from the attacker's side. The credential is the vendor's, and it is valid in every tenant that ever consented to the app. Whoever holds it can loop over the customer list and collect a token per tenant. That is exactly the "sorted GUID order, a few seconds apart" pattern Huntress saw on 15 October. Several consequences follow, and each one breaks a control most of us rely on:

  • No MFA. There is no user, so there is no second factor to ask for. BleepingComputer reports the attacker signed in directly as the backup app, with its secret, through scripts, so MFA never came into play.
  • No user Conditional Access. Policies that target users do not apply to app-only tokens. Location rules for applications need Conditional Access for workload identities, which few tenants have.
  • Not in the sign-in log you look at. App-only sign-ins go to Service principal sign-ins, a separate tab and a separate log category (ServicePrincipalSignInLogs). ConnectWise had to tell customers explicitly not to search the default user sign-ins view.
  • No endpoint at all. The attacker never touched a device of the victim. The EDR, the firewall and the proxy are all outside the path.
  • Revoking sessions does nothing. Disabling the service principal stops new tokens, but a token already issued stays valid until it expires, up to about 90 minutes. Resetting user passwords is irrelevant.

From reading data to owning the tenant

Backup only needs to read. But some of the ConnectWise Cloud Management apps had been granted much more, and Microsoft assessed that the actor likely abused Directory.ReadWrite.All. Write permissions over the directory, roles or applications are where reading turns into owning, because Microsoft Graph lets an app act on other principals, including itself. Two Graph calls are enough for the whole persistence chain:

# 1. Put a service principal (here: itself) in a directory role
POST https://graph.microsoft.com/v1.0/roleManagement/directory/roleAssignments
{ "principalId": "<its own service principal id>",
  "roleDefinitionId": "62e90394-69f5-4237-9190-012177145e10",   # Global Administrator
  "directoryScopeId": "/" }

# 2. Add a new secret to ANOTHER application it now controls
POST https://graph.microsoft.com/v1.0/servicePrincipals/<other app>/addPassword
{ "passwordCredential": { "displayName": "...", "endDateTime": "2028-..." } }

That is what happened in one partner tenant: ConnectWise Cloud Management - MS Teams added itself to Global Administrator, then a script with the user agent Python-urllib/3.12 added client secrets to an MSP management application and to the Huntress Security Platform app. The whole sequence took about five minutes. The new secrets are the real backdoor: they belong to apps nobody suspects, they survive the vendor rotating its own credential, and they survive every password reset in the tenant.

ARTEX: why the speed matters

ARTEX is public on GitHub (AGPL-3.0), and several forks translate it to English, Korean and other languages. It is a self-hosted system: a Go backend with an embedded Next.js interface and PostgreSQL. Its design explains what Microsoft observed:

  • A goals agent breaks a target down and extracts the scope.
  • A single planner is the only agent that creates new intents. It wakes up whenever the knowledge graph changes and pushes work into a frontier queue.
  • Many worker agents (goroutines, one planner and N workers per task) each take one intent, run it with tools (a Kali, Bash and HTTP toolset, nmap among them), and write what they learned back.
  • Two graphs hold the state: a shared asset graph (domains, subdomains, IPs, services, apps, endpoints) and a per-task exploration graph (goals, intents, facts, findings) linked by "spawns" and "proves" edges.
  • It can drive models from Anthropic, OpenAI or a local Ollama instance, so a capable operator does not depend on any single provider.

Put that together and you get what Microsoft describes: agents that run continuously, chase several paths at once, and turn a finding into the next action in seconds. Peak spraying hit about 2,900 attempts a minute. Some tenants went from first targeting to privileged access in less than three hours.

For a SOC, the lesson is not "detect AI". Nothing in these logs says an LLM was involved. The lesson is about time. If your process for a "new credential added to an application" alert is a ticket that someone opens tomorrow morning, an agent has already used that credential, pivoted and planted the next one. The rules below are cheap and quiet enough to run in real time, and the response steps assume you act within the hour.

foreach ($id in $ids) {
  Get-MgServicePrincipal -Filter "appId eq '$id'" |
    Select-Object DisplayName, AppId, Id, AccountEnabled

# 2. Every directory role held by a service principal (any vendor, not only ConnectWise)
Get-MgRoleManagementDirectoryRoleAssignment -All -ExpandProperty RoleDefinition |
  ForEach-Object {

    if ($sp) { [pscustomobject]@{ App = $sp.DisplayName; AppId = $sp.AppId; Role = $_.RoleDefinition.DisplayName } }

# 3. Secrets and certificates created since 13 October 2026, on applications and service principals
$since = Get-Date "2026-10-13"
Get-MgApplication -All -Property DisplayName,AppId,PasswordCredentials,KeyCredentials |

    $app = $_

Anything you cannot tie to a person and a ticket goes into the investigation. A secret with an end date years away, created by nobody you know, is the classic sign. In Cortex XDR, the same inventory from telemetry, every service principal sign-in by these apps since 1 October grouped by source:

The real service authenticates from Azure private IPv6 space. Public IPv4 sources, and above all the 144.172.64.0/24 range, are what you are looking for. If this returns nothing at all, check that service principal sign-ins are collected in the first place before you conclude anything.

Step 2: detect it, one layer at a time

The rules are compiled from one YAML source to both languages. In Cortex XDR they read the Office 365 / Entra ID data source: audit records in msft_azure_ad_audit_raw and sign-ins in msft_azure_ad_raw, with columns named after the Microsoft Graph directoryAudit and signIn resources. In Splunk they read azure:monitor:aad from the Splunk Add-on for Microsoft Cloud Services, through an azure_monitor_aad macro. Each query starts by flattening the nested JSON (initiator, targets, additional details) into plain columns, so the logic is the same on both platforms.

Layer 0: the spray, at machine speed

Before the supply chain path, Storm-0940 sprayed. Humans spray slowly to stay under lockout thresholds; agents do not care. Count failures per source address per minute, together with the number of distinct accounts:

Cortex XDR: password spray per source per minute

config case_sensitive = false
| dataset = msft_azure_ad_raw
| filter userPrincipalName != null
| alter error_code = json_extract_scalar(status, "$.errorCode")
| filter error_code in ("50126", "50053", "50055", "50057")      // bad password, locked, expired, disabled
| bin _time span = 1m
| comp count() as failures, count_distinct(userPrincipalName) as accounts by _time, ipAddress
| filter failures >= 30 or accounts >= 10
| sort desc failures

Splunk: same idea

`azure_monitor_aad` category=SignInLogs properties.status.errorCode IN (50126, 50053, 50055, 50057)
| bin _time span=1m
| stats count as failures dc(properties.userPrincipalName) as accounts by _time properties.ipAddress
| where failures >= 30 OR accounts >= 10
| sort - failures

Lockout code 50053 dominating the results, as it did here (almost 98% of the activity), is a sign of a spray that does not care about being noisy. Take the source addresses and look for any success from them, in user and in service principal sign-ins.

Layer 1: the vendor app signs in from the wrong place

The highest-value signal for this specific campaign: one of the seven apps authenticating from public IPv4, or from the actor's ranges.

The general version works for every vendor you trust, and it is the one I would actually leave running: a multi-tenant app signing in from an address it has never used before. Set the time range to 30 days:

Cortex XDR: service principals signing in from a new address in the last 24 hours

config case_sensitive = false
| dataset = msft_azure_ad_raw
| filter to_string(signInEventTypes) contains "servicePrincipal"
| alter error_code = json_extract_scalar(status, "$.errorCode")
| filter error_code = "0"
| comp min(_time) as first_seen, count() as signins by appDisplayName, appId, ipAddress
| alter hours_since_first = timestamp_diff(current_time(), first_seen, "HOUR")
| filter hours_since_first <= 24
| sort asc first_seen

Two ways to escalate, two rules. First, a high-privilege permission granted to an app, the step that makes everything else possible. Granting these should happen a few times a year, during vendor onboarding, with a named owner.

Layer 3: the backdoor, new secrets on other apps

The step that outlives everything else. Real admins add secrets as users, through the portal, from a browser. A secret added by an application, or by a scripting client, is worth an alert every time. The user agent is not in the top-level record: Entra stores it in the audit record's additionalDetails, which is why the query extracts it first.

DL-0077 Secret or certificate added to an Entra ID app by another app or by a scriptrule page and tests

Cortex XDR (XQL)

config case_sensitive = false
| dataset = msft_azure_ad_audit_raw
| filter activityDisplayName != null

Layer 4: the chain, correlated

Each rule above stands alone, but the campaign's signature is the sequence: one application taking a role and adding credentials within the same hour. This hunt groups the audit log per initiating app per hour and keeps the apps that did both:

Cortex XDR: an application that took a role and added credentials in the same hour

config case_sensitive = false
| dataset = msft_azure_ad_audit_raw
| alter initiating_app = json_extract_scalar(initiatedBy, "$.app.displayName")
| filter initiating_app != null
| filter activityDisplayName in ("Add member to role", "Add service principal credentials",
                                 "Add app role assignment to service principal")
    or activityDisplayName contains "Certificates and secrets"
| bin _time span = 1h
| comp values(activityDisplayName) as operations, count() as changes by _time, initiating_app
| alter took_role = array_length(arrayfilter(operations, "@element" contains "to role")),
        added_creds = array_length(arrayfilter(operations, "@element" contains "credentials" or "@element" contains "secrets"))
| filter took_role > 0 and added_creds > 0
| sort desc _time

Splunk: same correlation

`azure_monitor_aad` category=AuditLogs properties.initiatedBy.app.displayName=*

Full tier: what the attacker did with the access

These need log sources you have to switch on, usually through diagnostic settings into an Event Hub that Cortex XDR reads into msft_azure_raw. They are worth it for any client that keeps secrets in Azure.

The Graph calls themselves. With Microsoft Graph activity logs enabled, you see the request, not only its result. These are the two calls from the escalation above, plus the older role-membership endpoint:

Cortex XDR: role assignment and new-credential calls in Graph activity logs

config case_sensitive = false
| dataset = msft_azure_raw
| filter category = "MicrosoftGraphActivityLogs"
| alter method = json_extract_scalar(properties, "$.requestMethod"),
        uri    = json_extract_scalar(properties, "$.requestUri"),
        app    = json_extract_scalar(properties, "$.appId"),
        ip     = json_extract_scalar(properties, "$.ipAddress"),
        ua     = json_extract_scalar(properties, "$.userAgent"),
        code   = json_extract_scalar(properties, "$.responseStatusCode")
| filter method = "POST"
| filter uri ~= "(?i)/(addPassword|addKey)$"
    or uri ~= "(?i)/roleManagement/directory/roleAssignments"
    or uri ~= "(?i)/directoryRoles/[^/]+/members"
    or uri ~= "(?i)/servicePrincipals/[^/]+/appRoleAssignments"
| fields _time, app, ip, ua, method, uri, code
| sort desc _time

Bulk Key Vault reads. Microsoft saw secrets read across several vaults in a short window. Their threshold is a good start: 20 or more successful SecretGet calls across 3 or more vaults by one identity in 15 minutes.

Cortex XDR: bulk Key Vault secret reads

config case_sensitive = false
| dataset = msft_azure_raw
| filter category = "AuditEvent" and operationName = "SecretGet"
| filter to_string(resultSignature) = "OK" or to_string(httpStatusCode) = "200"
| alter caller_app = json_extract_scalar(identity, "$.claim.appid")
| bin _time span = 15m
| comp count() as secret_reads, count_distinct(resourceId) as vaults, values(callerIpAddress) as ips by _time, caller_app
| filter secret_reads >= 20 and vaults >= 3
| sort desc secret_reads

The hunts in this post are not, and none of it ran on a live tenant. Step 3: respond

Order matters here, because the evidence lives in the configuration you are about to change, and the logs expire fast (7 days of Entra logs on free tenants, 30 with P1 or P2).

  1. Disable, do not delete. For each of the seven apps, open the enterprise application and set "Enabled for users to sign-in?" to No. This also blocks new app-only tokens. Deleting the service principal destroys its permissions, owners and credentials, which are your evidence.
  2. Export the logs now. Audit logs, user and service principal sign-ins, the M365 unified audit log and Graph activity logs if you have them. Do not let the export delay containment, but do it the same hour.
  3. Review from 1 October, not from the advisory. Microsoft recommends at least 15 October and service principal sign-ins from 1 October. Look at failed sign-ins too, and do not limit the search to the published IPs.
  4. Remove what was added. Directory roles held by service principals you did not intend, app role assignments and consent grants nobody owns, and every secret or certificate since 13 October that you cannot explain. Check app owners as well.
  5. Rotate what was readable. Key Vault secrets read during the window, credentials of the other apps that got new secrets, and anything stored in mailboxes or SharePoint that the backup app could read.
  6. Wait out the tokens. Tokens issued before you disabled the app work for up to about 90 minutes. Keep watching Graph activity for that long after containment.
  7. Re-enable only on the vendor's word. ConnectWise asked customers to keep connections disabled until it sends restoration instructions directly.

What I am changing as an MSSP

The uncomfortable part of this story is that MSPs and MSSPs are the trusted app. A few things I now treat as non-negotiable for every client tenant:

  • Inventory every multi-tenant app and what it can do. Most tenants have dozens of vendor service principals with application permissions nobody remembers granting.
  • Treat RoleManagement.ReadWrite.Directory, AppRoleAssignment.ReadWrite.All and Application.ReadWrite.All as Global Administrator. Because they are: any app holding one can make itself Global Administrator.
  • Ingest service principal sign-ins and the audit log for every client, even the ones that send nothing else. It costs almost nothing and it is the only place this attack is visible.
  • Baseline where each vendor app signs in from, and alert on the first new address. That single hunt would have caught the token sweep within minutes.
  • Restrict user consent and use Conditional Access for workload identities where the license allows, to pin vendor apps to their known locations.
